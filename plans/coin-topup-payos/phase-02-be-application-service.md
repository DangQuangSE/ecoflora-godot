# Phase 2: BE Application Service — PayOS Integration + Business Logic

**Repo:** `D:\GitHub\eco-backend`
**Covers spec stories:** P1 "select package → get checkout link" (FR-04), P1 "auto-detect payment" (FR-05), P1 "credit exactly once" (FR-06), P2 "expired order" (FR-07).

## Requirements
After this phase, an application-layer service exists that can create a PayOS payment link and persist a `Pending` order, return PayOS's own hosted `checkoutUrl` verbatim (no QR rendering on our side — the login-gated web top-up page just opens that URL), report current order status (auto-expiring stale `Pending` rows), and process a verified PayOS webhook to credit `User.Currency` exactly once — all driven through `IUnitOfWork` transactions consistent with `DailyTaskService.ClaimTaskAsync`/`VitalityService.ClaimAsync`.

## Steps
1. Add the `payOS` SDK NuGet package to the appropriate project (`Application.csproj` if the SDK call belongs in application logic, or `Infrastructure.csproj` if treated as an external-service dependency — keep consistent with where other external integrations like Cloudinary currently live), and add a config-bound options class for `ClientId`/`ApiKey`/`ChecksumKey`.
2. Define `IPaymentService` (or `ICoinTopUpService`, matching existing `I*Service` naming) with `GetPackagesAsync`, `CreateOrderAsync(userId, packageId)`, `GetOrderStatusAsync(userId, orderCode)`, and `HandleWebhookAsync(rawPayload, signatureHeader)`.
3. Implement `CreateOrderAsync`: validate the package is active, generate a unique numeric `OrderCode` (timestamp-ms suffixed with a short random/sequential component, not a GUID — PayOS requires a numeric `orderCode`), call the PayOS SDK's `createPaymentLink` with amount/description/return/cancel URLs (pointed at the web partner's routes), and — only after a successful PayOS response — persist a `Pending` `PaymentOrder` row with `ExpiresAt = CreatedAt + 15 minutes`. If the insert hits the unique-constraint violation on `OrderCode` (collision), catch it and retry with a freshly generated code, bounded to 2 attempts before surfacing an error. Return PayOS's `checkoutUrl` response field as-is alongside `orderCode`/`expiresAt` — **no QR rendering, no image library** (this changed from the original in-app design; see plan.md Research Summary item 2). On PayOS call failure, return an error with no `PaymentOrder` row left behind (per NFR "Availability").
4. Implement `GetOrderStatusAsync`: look up the order by `OrderCode` scoped to the requesting user (read-only, no tracking), and if still `Pending`/`Expired`-but-recent and past `ExpiresAt`, first attempt the backup reconciliation check (next step, itself rate-limited) before falling back to marking it `Expired`; return `Status` and, if `Paid`, the current `User.Currency`.
5. Implement the backup reconciliation check (usable both from the lazy path in step 4 and from the mandatory background sweep in step 5b): for an order in `Pending` or recently-`Expired` past a short grace window (~3 minutes), **first check `LastReconciliationAt`** — skip the PayOS call entirely if less than 30 seconds have passed since the last attempt (just return current local status), otherwise stamp `LastReconciliationAt = now` and call PayOS's GET payment-link-status API. This caps PayOS API calls per stuck order to roughly one per 30s regardless of client poll frequency. If PayOS reports paid, run the same atomic credit path as the webhook handler (step 6); if PayOS reports cancelled, mark the order `Cancelled`; if PayOS reports still pending/expired with no successful payment, leave/transition to `Expired` once past `ExpiresAt`.
5b. **(Required, not a stretch addition)** Implement a small `IHostedService` background sweep running every few minutes that calls the step 5 reconciliation check over all `PaymentOrder` rows in `Pending` or recently-`Expired` past their grace window. This is the only safety net for a player who pays and then immediately backgrounds/closes the app before any poll tick can observe the result — without it, such an order can never resolve to `Paid` even though PayOS successfully charged the player. Required for this phase to be considered complete.
6. Implement `HandleWebhookAsync`: verify the PayOS checksum signature on the raw payload before touching the DB (reject with no write on failure, per NFR "Security"); log the verification outcome (success/failure) and a redacted summary of the payload for support/audit purposes regardless of outcome — this project has no ledger table, so application logs are the only trail for "what did PayOS tell us and when." On a verified PAID event: call `dbContext.PaymentOrders.Where(o => o.OrderCode == orderCode && (o.Status == Pending || o.Status == Expired)).ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, Paid).SetProperty(o => o.PaidAt, now))` — note the guard is `Pending OR Expired`, not `Pending` alone, so a payment that completes right as the order crosses its 15-minute boundary (or after the sweep already flipped it to `Expired`) still gets credited instead of being silently dropped. Check the affected-row count; only if it's exactly 1, separately load the order's `CoinPackageId` → resolve `CoinPackage.CoinAmount` **from that server-side row, never from any amount/coin field in the webhook payload itself** (the payload is attacker-influenced input even after signature verification confirms it came from PayOS — verification proves authenticity of *PayOS's* claim, not that the claimed amount matches what this order was created for), and increment `user.Currency` by that package's `CoinAmount` inside the same transaction. A second identical webhook call finds the order already `Paid` (affected-row count 0) and is a no-op — no double credit. On a verified CANCELLED event, run the equivalent `ExecuteUpdateAsync` guarded on `Pending` only, transitioning to `Cancelled`.
7. Register the new service(s), the `IHostedService` sweep, and PayOS SDK client in `Program.cs` DI, matching the `AddScoped<IXService, XService>()` / `AddHostedService<T>()` patterns used elsewhere.
8. Add automated test coverage for the logic that doesn't require live PayOS credentials: webhook signature verification (valid/invalid/missing), the idempotent-credit guard via `ExecuteUpdateAsync` (simulate two identical PAID payloads, assert `User.Currency` increments exactly once via a fresh DB read), a test asserting the credited amount equals `CoinPackage.CoinAmount` even when the webhook fixture's payload amount field is deliberately tampered/mismatched, the `Pending`→`Expired` transition, and the late-PAID-webhook-on-`Expired`-order case (assert it still transitions to `Paid` and credits coin). If no test project exists yet in the solution, scaffold a minimal xUnit project (e.g. `Application.Tests`) following standard .NET conventions before adding these tests.

## Success Criteria
- A fixture-based unit test sending the same PAID webhook payload twice results in `User.Currency` increasing by exactly one package's `CoinAmount`, verified by re-reading the DB row (not just the HTTP response), with the second call's `ExecuteUpdateAsync` affecting 0 rows.
- A fixture-based unit test with a tampered amount/coin field in an otherwise-validly-signed webhook payload still credits exactly `CoinPackage.CoinAmount` (resolved server-side via `PaymentOrder.CoinPackageId`), not anything derived from the payload.
- A fixture-based unit test with an invalid/missing PayOS signature results in zero DB writes (order status unchanged, `User.Currency` unchanged).
- A fixture-based unit test for an order whose `ExpiresAt` has passed and remains unpaid reports `Expired` from `GetOrderStatusAsync` instead of `Pending`.
- A fixture-based unit test for a PAID webhook arriving for an order already transitioned to `Expired` still credits the coin and transitions it to `Paid` (guard is `Pending OR Expired`, not `Pending` alone).
- `dotnet build` succeeds with the PayOS SDK package restored and referenced correctly.
- Code review confirms `CreateOrderAsync` never leaves a `Pending` `PaymentOrder` row when the upstream PayOS call fails, and confirms no code path loads a `PaymentOrder`, checks its status in C#, then calls `SaveChangesAsync()` for the Paid/Cancelled transition (must be `ExecuteUpdateAsync` with an affected-row check instead).

## Risks
- HIGH: No PayOS credentials yet — `CreateOrderAsync`'s real `createPaymentLink` call and the reconciliation sweep's live GET status call cannot be exercised end-to-end. Mitigation: write the SDK calls against PayOS's documented contract, unit-test signature verification and credit logic with hand-built sandbox-shaped JSON fixtures, and leave the live-call manual verification as a follow-up once credentials exist.
- MEDIUM: Webhook signature verification must use the exact algorithm/field ordering PayOS expects — using the SDK's built-in verification method (per resolved decision #1) rather than reimplementing HMAC reduces this risk significantly.
- LOW: Concurrent webhook + reconciliation sweep racing on the same order — both are guarded by the same `ExecuteUpdateAsync ... WHERE Status IN (Pending, Expired)` atomic update, so whichever commits first wins and the other's update affects 0 rows; needs a test asserting no double-credit under that race shape.
- LOW: If `createPaymentLink` succeeds at PayOS but the process crashes/times out before the local `Pending` row is persisted, a real payable PayOS link exists with zero local record (cannot be reconciled, cannot double-credit either since no local row references it). Accepted residual risk for MVP — very low probability, no money-loss-to-user or double-credit exposure, just a wasted PayOS-side link.
- LOW: The webhook endpoint must read the raw request body for signature verification (the PayOS SDK's verify method needs the exact bytes PayOS signed) — ASP.NET Core's default JSON model binding can consume/transform the body before a raw-bytes read happens if not configured carefully. Mitigation: bind the webhook payload as a raw `string`/`byte[]` (or read `Request.Body` directly with buffering enabled) rather than a typed DTO, verify signature against those exact raw bytes, and only deserialize into a DTO after verification passes.
