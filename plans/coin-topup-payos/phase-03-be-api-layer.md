# Phase 3: BE API Layer — Endpoints, Validation, Config

**Repo:** `D:\GitHub\eco-backend`
**Covers spec stories:** all P1 stories (package listing, order creation, status polling) and FR-06/FR-08 (public webhook endpoint, config placeholders) — this phase exposes Phase 2's service over HTTP for the login-gated web top-up page to consume.

## Requirements
After this phase, the 4 endpoints from spec FR-03..FR-08 are reachable, request bodies are validated via the existing FluentValidation auto-pipeline, responses follow the project's `ApiResponse<T>`/`ApiError` envelope and are documented with `ProducesResponseType`, and PayOS credentials are read from configuration with placeholder values committed (no real secrets in source). These endpoints are consumed by a web partner's frontend, not the Godot client — response shapes are the cross-team contract.

## Steps
1. Define request/response DTOs under `Application/DTOs/Payment/` (e.g. `CoinPackageDto`, `CreateOrderRequest { PackageId }`, `CreateOrderResponse { OrderCode, CheckoutUrl, ExpiresAt }`, `OrderStatusDto { Status, NewCurrencyTotal? }`), matching the plain-DTO style of `Application/DTOs/DailyTask/*.cs`. `CheckoutUrl` is PayOS's own hosted payment page URL — no QR image field anywhere in these DTOs.
2. Add `CreateOrderRequestValidator` under `API/FluentValidation/` validating `PackageId` is present/non-empty, following the style of `BuyItemRequestValidator.cs`/`UpdateDailyTaskConfigValidator.cs` (auto-wired by the existing FluentValidation pipeline registration in `Program.cs` — no manual `ModelState` checks needed in the controller).
3. Create `PaymentsController` under `API/Controllers/` with `[Authorize(Roles = Constant.Roles.Player)]` (matching `VitalityController`) exposing `GET /api/coin-packages`, `POST /api/payments/orders`, and `GET /api/payments/orders/{orderCode}/status`, each delegating to the Phase 2 service and translating `(Success, Error)` tuples into `Ok`/`StatusCode` responses exactly like `VitalityController.Claim`.
4. Add the public webhook endpoint `POST /api/payments/webhook` either on the same controller (with `[AllowAnonymous]` overriding the controller-level `[Authorize]`) or a dedicated `PaymentWebhookController` with no `[Authorize]` at all — confirm which matches the project's existing convention for public endpoints (check `AuthController` for precedent) before deciding; the handler reads the raw body and the PayOS signature header, then calls the Phase 2 `HandleWebhookAsync`.
5. Annotate every endpoint with `[ProducesResponseType]` for success and relevant error codes (400/401/404/409 as applicable), matching the density of annotations on `VitalityController`/`AdminDailyTasksController`.
6. Add the PayOS config section (`ClientId`, `ApiKey`, `ChecksumKey`) to `API/appsettings.json` (and `appsettings.Development.json` if secrets are normally split there) with empty/placeholder string values and a code comment noting real values are filled in once the merchant account exists; bind it via `IOptions<PayOsOptions>` in `Program.cs` DI registration alongside the Phase 2 service wiring.
7. Add controller-level integration/smoke tests (or, if no test project exists per Phase 2 step 8's scaffolding, extend that same test project) covering: `GET /api/coin-packages` returns the 4 seeded packages, `POST /api/payments/orders` with an invalid `packageId` returns 400, and the webhook endpoint rejects an unsigned request with no DB mutation — reusing the Phase 2 fixtures where possible.
8. Manually verify (via Swagger UI or an HTTP client) that all 4 endpoints appear correctly in the OpenAPI spec with the expected request/response shapes, since this is the cross-repo contract the web partner's frontend will be built against — write down the exact field names/types to hand off to them.

## Success Criteria
- Swagger UI lists `GET /api/coin-packages`, `POST /api/payments/orders`, `GET /api/payments/orders/{orderCode}/status`, and `POST /api/payments/webhook` with documented request/response schemas.
- A manual `GET /api/coin-packages` call (authenticated) returns exactly the 4 seeded packages with `priceVnd`/`coinAmount` fields.
- A manual `POST /api/payments/orders` call with a valid `packageId` returns 200 with a non-empty `checkoutUrl` string, an `orderCode`, and an `expiresAt`, even though the underlying PayOS call may need sandbox credentials to fully succeed end-to-end (see Phase 2 Risks).
- A webhook call with a missing/invalid signature returns a non-2xx response and produces no DB change, verified by re-querying the order row.
- `dotnet build` succeeds and FluentValidation correctly rejects a `POST /api/payments/orders` request with a missing `packageId` (400, no controller-side manual check needed).

## Risks
- LOW: No cap on concurrent `Pending` orders per user — a buggy/malicious client could spam `POST /api/payments/orders`, each call hitting PayOS's billable `createPaymentLink` API. Not a money-loss risk (no credit without a paid webhook) but a cost/availability risk against the PayOS account. Acceptable to skip for MVP given expected traffic; worth a follow-up cap (e.g. reject if the user already has an unexpired `Pending` order) if abuse is observed.
- HIGH: Without real PayOS credentials, the full happy path (`POST /api/payments/orders` → real QR → real webhook) cannot be manually verified end-to-end through Swagger/Postman — only the validation/rejection paths and Phase 2's fixture-based unit tests are verifiable now. Mitigation: explicitly note this as a follow-up manual test once credentials are registered; do not block this phase's completion on it.
- MEDIUM: Deciding `[AllowAnonymous]` placement for the webhook vs. a fully separate controller affects whether the existing `[Authorize(Roles = Constant.Roles.Player)]` convention accidentally leaks onto the public route. Mitigation: write a quick anonymous-request smoke test against the webhook route specifically to confirm it's reachable without a JWT.
- LOW: Response field naming/casing mismatch between what this phase ships and what the web partner's frontend expects (`checkoutUrl` vs `checkout_url`, etc.) — mitigate by freezing the exact response shape here and handing the partner a short contract note (field names/types) once this phase ships, updating spec.md's field names if they drift during implementation.
